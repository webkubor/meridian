## 七条阻断级缺陷（已由本人逐条核对源码确认）

### [BR-01] branch_checkout never deserializes: UI sends opts:{} but Rust CheckoutOptions.detach is a required field

- 类别：arg-shape
- 证据：/tmp/meridian-baseline/src-tauri/src/domain/refs.rs:41-45 — `#[derive(...)] #[serde(rename_all = "camelCase")] pub struct CheckoutOptions { pub detach: bool }` has NO #[serde(default)] on the struct or the field, so `detach` is a required key. /tmp/meridian-baseline/src/bridges/commands.ts:152-158 defaults `opts: CheckoutOptions = {}` and always sends `args: { repo, name, opts }`. The only call site, /tmp/meridian-baseline/src/stores/branches.ts:63, is `commands.branchCheckout(repo, name, {})`. /tmp/meridian-baseline/src-tauri/src/commands/branches.rs:104-105 has `#[serde(default)]` on `opts` only (that default applies when `opts` is absent, not when it is `{}`). /tmp/meridian-baseline/src/bridges/bindings.ts:233-235 declares `detach?: boolean` (optional), so the TS side believes it may omit it. CLAUDE.md:68-69 states the invariant this breaks: 'every field the frontend can omit carries #[serde(default)]'.
- 预期：HEAD switches to the branch, a success toast '已签出分支 X' appears, and the working copy/branch list reload.
- 实际：Tauri fails while deserializing the command arguments (missing field `detach`), before AppState::run is ever entered, so the engine never runs and HEAD never moves. The rejection is not an ErrorPayload, so App.vue:548-554 reportError() cannot read `.message` and falls back to the generic toast '无法签出该分支。' ('Could not check out the branch.') with no cause — exactly the owner's 'fails with no error shown'. Checkout is unreachable from every entry point in the branch surface.
- 修复：Add `#[serde(default)]` to CheckoutOptions (container level) in src-tauri/src/domain/refs.rs, matching the crate convention used by MergeOptions/RebaseOptions (commands/integrate.rs:78-79, 226-227). Optionally also change the bridge default to an explicit `{ detach: false }` so the payload is self-describing. Independently, make reportError() fall back to `errorText()` (see BR-07) so a non-ErrorPayload rejection still tells the user something.

### [F1-fetch-arg-shape] Toolbar Fetch always fails: `remote_fetch` is sent a string where Rust expects a struct

- 类别：arg-shape
- 证据：src/bridges/commands.ts:291-298 — `remoteFetch(repo, remote, refspecs = [], mode = "default")` always includes `mode` in the payload: `invoke("remote_fetch", { args: { repo, remote, refspecs, mode } })`. src/bridges/bindings.ts:485 declares `RemoteFetchMode = "default" | "prune" | "tags" | "pruneTags"`. Rust's field is a struct: src-tauri/src/commands/refs.rs:40 imports `RemoteFetchMode` from `crate::engine::remotes`, and src-tauri/src/engine/remotes.rs:56-65 defines it as `struct RemoteFetchMode { prune: bool, tags: TagFetch, depth: Option<i32> }` with `#[serde(default, rename_all = "camelCase")]`. src-tauri/src/commands/refs.rs:687-694 is the args struct (`#[serde(default)] pub mode: RemoteFetchMode`) — `default` only applies when the key is ABSENT, and the frontend always sends it. Only caller: src/composables/useGit.ts:56-61. docs/03-command-surface.md:241 documents the wire shape as `opts{prune, tags, ...}`, confirming the intent.
- 预期：`git fetch <remote>` runs, the remote-tracking refs update, FetchReport is returned and the branch list's ahead/behind badges refresh.
- 实际：The promise rejects with a serde string ("invalid type: string \"default\", expected struct RemoteFetchMode"). useGit.run (useGit.ts:45-47) stores that raw string in `lastError`; runVerb (App.vue:580-584) shows only the generic "操作失败。" toast and records `error.message === undefined` in the activity list. Fetch has never worked in this build, and the failure reads like a network problem rather than a broken call.
- 修复：Stop sending the key from the wrapper — omit `mode`/`refspecs` unless the caller supplies them so the Rust `#[serde(default)]` applies — and type the parameter as the Rust struct (`{prune?: boolean; tags?: TagFetch; depth?: number}`). Better: rename the engine struct (e.g. `RemoteFetchOptions`) so it stops colliding with `domain::repository::RemoteFetchMode`, which is a different two-value enum (domain/repository.rs:187-196). Also wire or refuse `remote_prune` — with the current defaults `prune:false` and no caller passing it, stale tracking refs can never be pruned from the UI.

### [BR-02] Checking out a remote-tracking branch whose short name already exists locally always fails

- 类别：logic
- 证据：/tmp/meridian-baseline/src/stores/branches.ts:72-86: `checkoutRemote` computes `suggestedName` = the short name ('main' from 'origin/main') and then deliberately passes `localName = nameExists ? undefined : suggestedName`. /tmp/meridian-baseline/src-tauri/src/engine/branches.rs:584 raises ReferenceExists when the local name is taken: `let name = local_name.unwrap_or(&short); if repo.find_branch(&name, Local).is_ok() { return Err(... "Branch '{name}' already exists") }` — and the same check is duplicated at 586-600. So when the local branch exists the UI withholds the name and the engine then re-derives exactly that name and refuses. Reached from /tmp/meridian-baseline/src/App.vue:855-869 (checkoutFlow's `branch?.isRemote === true` arm), i.e. row dblclick (App.vue:1592), the checkout dialogue (App.vue:842-849 lists allBranches with emitFullName), and the palette only lists locals so it is unaffected.
- 预期：Switch to the existing local branch `main` (what `git checkout main` does), or, if the user really wants a second branch at origin/main's tip, ask for a distinct name.
- 实际：English toast 'Branch \'main\' already exists' in the zh-CN UI and no checkout. The obvious intent — get onto main — is refused with no way forward, because nothing in the branch surface exposes a name prompt for this verb.
- 修复：In stores/branches.ts:72-86, when `nameExists` is true, check out the existing local branch instead of calling checkout_remote (i.e. fall through to `commands.branchCheckout(repo, suggestedName)`), or pass a de-duplicated name such as `main-2` and surface it in the toast. Fix the engine's duplicated existence check at engine/branches.rs:586-600 at the same time.

### [F2-push-stale-head] Toolbar Push pushes the branch that was checked out when the repo was opened, not the current HEAD

- 类别：logic
- 证据：src/composables/useGit.ts:75-84 — `const branch = branchName ?? repos.selected?.headBranch`. src/App.vue:671-672 calls `git.push()` with no argument. `repos.selected` is `repositories.value.find(...)` (src/stores/repos.ts:27-29) and the only writer of `repositories` is `upsert` (repos.ts:36-43), called from open/init/clone only (repos.ts:61, 78, 124). Nothing refreshes RepoInfo afterwards: useAppEvents.ts:26-29 makes `reposChanged` a no-op, and there is no `repositoryRefresh` wrapper in src/bridges/commands.ts although the Rust command is registered at src-tauri/src/lib.rs:69. `headBranch` is read as "the current branch" in four other places (App.vue:207, 225-226, 596, 847, 1608), so the staleness is visible beyond push.
- 预期：`feature` is published — the toolbar's own disabled reason (App.vue:609, zh-CN "HEAD 处于游离状态 —— 请先签出分支再推送。") promises the verb means "push HEAD".
- 实际：`repos.selected.headBranch` is still "main", so `remotePublishBranch(id, "origin", "main")` re-pushes main. Because origin already has main, the push is a no-op fast-forward that succeeds, and the toast claims 已推送. `feature` is never published; its row still shows ahead>0 with no upstream, and the window subtitle still says "在 main 上".
- 修复：Resolve the branch from the live branch list (`branches.branches.value.find(b => b.isHead)?.name`) or pass the branch down from the list, and add a `repositoryRefresh` bridge so RepoInfo.headBranch is re-read on refsChanged (which also fixes the stale subtitle and the "Merge into <old branch>" label).

### [SHELL-01] Commit composer survives a repository switch, so the next commit amends the wrong repository's HEAD

- 类别：logic
- 证据：src/App.vue:935-938 declares composerSubject/composerBody/composerAmend/composerSignOff; the only place they are cleared is App.vue:1005-1007 inside commitNow() after a successful commit. The existing repository watch App.vue:520-524 (`watch(activeRepoId, (id) => compare.forRepo(id ?? null))`) resets compare but nothing resets the composer. commitNow() (App.vue:987-1014) sends whatever is in those refs to workingCopy.commit -> commitAmend/commitCreate (src/stores/workingCopy.ts:68-84) with repo = repos.selectedId, i.e. the NEW repository. The switcher is always enabled (App.vue:1417 `:locked="false"`), so the switch is reachable mid-edit.
- 预期：Switching the selected repository resets the composer (subject, body, amend, sign-off) — no input meant for repository A can be submitted against repository B.
- 实际：composerSubject/composerBody/composerAmend/composerSignOff are shell-level refs that outlive the repository selection, so A's message and A's amend tick are applied to B, silently rewriting an unrelated repository's HEAD commit.
- 修复：In the existing `watch(activeRepoId, ...)` at App.vue:520-524, clear composerSubject.value = "", composerBody.value = "", composerAmend.value = false, composerSignOff.value = false (and selectedPath.value = null, conflictedOnly.value = false) whenever the id actually changes.

### [WC-01] Discarding an untracked file reports success and deletes nothing (includeUntracked never sent)

- 类别：silent-failure
- 证据：src/bridges/commands.ts:191-197 sends `{args:{repo, paths, opts}}` with opts defaulted to `{}`; src/stores/workingCopy.ts:52-61 calls it with no options; the only caller is App.vue:918. src-tauri/src/engine/index.rs:269-273 hits `if status.contains(Status::WT_NEW) && !tracked { if opts.include_untracked { to_delete.push(..) } continue; }` — with include_untracked=false the path is skipped and the function returns Ok(()) having written nothing; src-tauri/src/domain/working_copy.rs:519-529 declares `include_untracked: false` by default, and src-tauri/src/commands/working_copy.rs:412-415 returns `changed(cx)` (a fresh delta still containing the file). App.vue:919 then pushes the success toast for `ok === true`.
- 预期：The untracked file is deleted (or the command refuses loudly so no success toast is shown).
- 实际：The engine skips the path (`include_untracked` defaults to false), returns Ok, and the UI shows the success toast 「已放弃该文件的改动。」 / "Discarded the file's changes." while the file and its row remain.
- 修复：The store/composable must pass the delete intent: `wcPathsDiscard(repo, paths, { includeUntracked: <any selected row is untracked>, confirmToken: "confirmed" })` after the confirmation dialogue (the engine already enforces the token at index.rs:222-233). Additionally, make the engine refuse when the selection is untracked-only and include_untracked is false, instead of silently doing nothing (a `paths_discarded` count or an ErrorPayload naming the untracked paths).

### [SHELL-02] HEAD is never re-read after a checkout, so the toolbar's Push and Commit & Push publish the wrong branch

- 类别：stale-ui
- 证据：RepoInfo (headBranch/headOid/state) is only written by repos.upsert, which is called solely from open/init/clone (src/stores/repos.ts:36-43, 61, 78, 124). branches.checkout (src/stores/branches.ts:60-70) runs branch_checkout then refresh() of the branch list only — it never updates RepoInfo, and useGit.refreshAll (src/composables/useGit.ts:32-34) refreshes branches/working-copy/history only. The engine command that would fix this, `repository_refresh` (src-tauri/src/commands/repository.rs:259-302, registered at src-tauri/src/lib.rs:69), has NO bridge in src/bridges/commands.ts and no entry in src/bridges/bindings.ts, so nothing in the UI can call it. Consumers of the stale value: windowSubtitle (App.vue:220-227, renders "On {branch}"), RepoSwitcher head label (src/layout/RepoSwitcher.vue:85), toolbar pushReason/detachedHead (App.vue:604-610), can-amend (App.vue:1483). git.push() with no name reads repos.selected?.headBranch (src/composables/useGit.ts:75-84) and the engine pushes that named ref: engine/remotes.rs:982 builds refspec `refs/heads/{branch}:refs/heads/{branch}`.
- 预期：After a checkout (in-app or external) the shell's repository model reflects the new HEAD, so the window subtitle, the switcher and every push path name the branch that is actually checked out.
- 实际：headBranch/headOid/state are frozen at open time; after a checkout the subtitle still reads "On main", and the toolbar Push / Commit & Push publish `main` while the user is on `feature` — a silent wrong-ref push to a remote, reported as success.
- 修复：Add a `repositoryRefresh(repo)` bridge for the already-registered `repository_refresh` and call it (or re-read RepoInfo via it) after every command that can move HEAD: branch checkout/create/rename/delete, commit/amend, merge/rebase/continue/abort, fetch/pull/push, discard. Alternatively have useGit.run refresh the RepoInfo of the repo it acted on and upsert it.

## 横切问题（审计员指出应一次性修，而不是逐条改）

1. The only guard against dead controls is structurally blind to exactly this failure mode. /tmp/meridian-baseline/src/interactionCompleteness.test.ts proves that 'every emitted event is listened for' by regexing event NAMES across all sources and asserting each name appears somewhere — so binding `@contextmenu="() => {}"` in App.vue satisfies it. Fifteen such bindings exist in App.vue alone (lines 1424, 1492, 1560, 1568, 1593, 1655, 1663, 1679-1682, 1686-1687, 1705, 1747). Every one of them renders a translated, enabled, screen-reader-announced control. Fix once, not per finding: make the check reject empty arrow bodies (and no-op identifiers), or delete the controls.
2. One `LoadState` type serves two different jobs — 'what should I render' and 'did the last action work' — and each store picks its own failure convention. branches turns throws into `null`/`false` plus a shared `lastError` (stores/branches.ts:46-95); history nulls the graph and swallows (stores/history.ts:79-84); repos empties `remotes` on failure (stores/repos.ts:49-51); workingCopy lets a mutation error replace the entire tab. The result is that 'failed' and 'there is none' are pixel-identical in every surface, and the message the user sees depends on which store the verb happened to go through. Fix once: one result type carrying the `ErrorPayload`, one reporting path, and mutation errors that never overwrite list state.
3. There is no in-flight guard and no cancellation anywhere in the app. `useGit.busy` is set and read by nobody; the only guard in the codebase is the `inFlight` promise in useApp.ts; the Rust queue serialises per repository but the UI neither shows nor blocks queued work. Every verb is double-clickable, fetch/push/clone/install cannot be abandoned, and every async store load (history query, branch list, remotes) is last-response-wins with no generation counter, so a slow earlier response can overwrite a faster later one. Fix once: a per-repo operation registry (start / settle / cancel + request token) that every verb goes through and that simultaneously drives the disabled state and the activity chip.
4. Selection and query state is duplicated between shell refs and the stores that own the data, and the copies silently drift. `branchSearch`/`branchFilter` (App.vue:1086-1087) never reach `useBranches.search`, so the engine-side `search` argument of `branch_list` is always empty; `historySearch`/`historyView` are shell refs that re-drive the store through an undebounced watcher (App.vue:1075); `selectedBranchName`, `selectedSidebarId`, `paletteQuery` are all shell-local. Fix once: one owner per piece of state, in the store, with the shell holding only view state that has no server meaning.
5. Limits and capacities are decided ad hoc per surface and mostly fail silently: diffs truncate at 40k lines, history pages at 250, branches load everything and filter locally, the activity list caps at 50, remotes load all. Each surface decides on its own whether truncation is visible, which is why the working-copy findings about silent diff truncation and about rows that can never appear are two instances of one missing contract. Fix once: a `Paginated`/`Truncated` field on `LoadState` that every load must state, rendered by one component.
6. Error presentation is decided at the call site, not at a boundary: raw engine English, a shell toast, or a ListShell error arm, chosen per verb; the i18n `errors.byCode` catalogue is bypassed. `useAppEvents` is the only place with a systematic rule (ignore events for another repo) and it does not extend to the stores' own awaits. Fix once: a single error-to-catalogue mapping at the reporting boundary, plus the repo-id check on every async store result.
7. Nothing re-reads state that changed outside the app's own commands. Refreshes come only from `refsChanged`/`workingCopyChanged` events and the explicit ⌘⇧R / palette refresh — no window-focus refresh, no file watcher — and even the manual refresh skips `compare` and the remotes list. An edit made in a terminal leaves the entire window stale until the user remembers the shortcut.
8. All state is global singleton state: one `repos.selectedId`, one history selection, one branch selection, one toast list, one dialogue queue, one activity list — with no per-window isolation and no request tagging. Every cross-repo correctness question in the findings (a status delta from the previous repo, an event arriving after a switch, a queue entry outliving its operation) is an instance of this one structural choice.
